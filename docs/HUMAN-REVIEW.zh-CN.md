# 正式评估的人工作业清单

本文件由助手准备，所有姓名、决定和勾选均待真人填写。它不是已完成的人工审核或独立标注证明。开发使用第 2、3 讲；最终评估使用第 4、6、8 讲。旧准备批次保留历史身份，不能直接充当当前代码、依赖和有效模型配置的正式冻结批次。

人工作业分为两个阶段：**采集前复核输入和执行协议**，决定测什么、怎样运行；**采集后独立标注和裁决**，判断系统实际输出是否正确、引用是否支持。前者不能代替后者，空白准备表也不能代替绑定实际输出的新表。

## 第一阶段：采集前复核

### 1. 原讲义与输入

- [ ] 对照 `data/mit-6.006-spring-2020/corpus.json` 核对第 4、6、8 讲的原 PDF、SHA-256、原始页数和教学页清单；保留完整归属页，但不将归属页当作教学证据。
- [ ] 逐题复核 20 个选择题作答、40 个简答作答、40 个证据问答和 20 个流程场景。当前候选输入来自 AI 编写，不能当作真实学生数据。
- [ ] 选择题有四个不同选项、明确含义和可核对的候选正确答案；检查题意清楚、讲义支持、答案正确及无重复。
- [ ] 简答评分点互不重复、等权、含义明确且受指定原教学页支持；索引采用从 0 开始的编号，命中比例至少 80% 才通过。
- [ ] 检查每个候选作答及引用的原始页码，不把 PDF 阅读器的重编号误作原页码。
- [ ] 独立核对 40 个证据问题是否可由冻结讲义回答；草稿中的“30 个可支持 / 10 个不可支持”是待审核设计，不是已经证实的标签。
- [ ] 题目、候选答案、评分点、作答、评估日志和人工判断均未加入讲义检索库。
- [ ] 需要修改输入时，保存审核修改记录；最终采集前固定新输入，不在看到最终输出后挑题或改标准。

### 2. 一讲一评估单元与真实夹具

当前应用会把一个 PDF 分成多个自然教学主题。流程采集器要求每个评估 chapter 覆盖**该讲完整教学页**；直接选择某个自然主题章通常不能满足要求。下面是可实现的候选构造顺序，仍需两人批准：

1. 按讲义记录原始文档 ID、全部自然主题章 ID、章顺序、概念和来源页。原课程的主题划分保持原样。
2. 建立单独的整讲候选：合并该讲主题章的概念，按首次出现顺序去重，并列出去重前后清单；概念相近但含义不同的项由成员判断，不由字符串规则替代审核。
3. 候选 `sources` 明确包含该讲 `teaching_pages` 的每一页，按原页码排列。不能把模型输出的来源页并集直接当作完整讲义，因为它可能漏页。核对解析正文未空缺、原 PDF 哈希/总页数正确。
4. 两人审核候选概念对整讲的代表性、完整教学页、来源映射及作答策略。候选聚合文件本身不代表审核通过。
5. 审核后将同一个候选导入新的专用评估课程，构造明确标注的“一讲一个评估 chapter”夹具；不改生产课程原章边界，不把该夹具称为自然 planner 的实际输出。使用项目存储函数映射新稳定 ID，保留构造来源和审核记录。
6. 为每个场景、每次重复建立 `shared`、`baseline`、`full` 三份独立夹具。20 场景 × 3 重复 × 3 角色共 180 个不同的 `(user_id, course_id, chapter_id)` 三元组。可用三个角色专用 `citepath_eval_...` 账户分别持有独立课程；是否采用该方式应提前记录，不能让练习或掌握历史跨场景流入。
7. 将观察到的真实 ID 填入 `workflow-bindings.json.cases`。三方概念顺序及每页正文指纹必须相同，每个夹具只关联对应的一份原 PDF，并覆盖完整教学页。夹具在首次采集前不得已有 practice 历史。

- [ ] 上述候选来源、整讲覆盖、概念及实际 ID 均已由两人逐项核对。
- [ ] 180 个夹具三元组全局不复用；原 PDF 哈希、总页数、活动状态和入库完成状态均正确。
- [ ] 重启场景有专用账户的本机凭据环境变量名和空闲的本机 API 端口，采集器只停止自己创建的进程。
- [ ] 证据问答另有两个不同的专用 baseline/full 课程，均包含完全相同的三讲冻结语料；每份运行时文档 ID 都映射到正确的冻结 ID、原 PDF 哈希和页数。

只在本机配置真实凭据。绑定 JSON 中保存的是环境变量**名称**，不能包含密码、API Key 或 Cookie。

### 3. 流程协议与作答策略

- [ ] 采用预先定义的 `actual_grade_v1`：根据真实整数成绩和已保存阈值检查状态，分别记录各轮，不用四舍五入显示值决定通过。
- [ ] baseline 共用实际首轮后只运行一轮；full 首轮通过即结束，否则只针对薄弱概念补第二轮，第二轮后必定结束。
- [ ] 两系统首轮的题目、作答、判分和反馈来自同一实际结果，记录相同的首轮指纹；不能各自生成不同首轮后声称配对。
- [ ] `reference` / `wrong_reference` 是固定测试作答策略，须由成员复核并提前冻结；它们不是学生表现、独立答案质量标签或被强制注入的正确数。
- [ ] 要求的首轮通过/补练分支若未出现，记录不匹配或未覆盖，不反复运行直到得到期望结果。
- [ ] 重启、保存草稿、独立问答、重复提交和最终结果重开各自有实际动作与检查，不能仅填写一个通用成功状态。
- [ ] 超时场景明确为批改器边界的一次受控故障，恢复后仍调用真实批改器；不把它说成真实提供方宕机。
- [ ] 旧的 159/200 等预设计数仅作为单独 synthetic 控制器用例，不能进入真实流程指标。
- [ ] 提前固定汇总规则：一个场景须三次重复均通过；第三轮、重复计分或问答修改成绩在任一系统出现都不能被平均数抵消。

### 4. 人工确认后再冻结

草稿状态应保留为：

```json
{
  "reviewed": false,
  "review_origin": null,
  "reviewed_by": [],
  "chapter_mapping_sha256": null,
  "response_policy_sha256": null
}
```

只有两人实际完成第一阶段后，才由其授权记录相应人工审核字段。不能把助手的检查结果变成人审声明。当前 real-final 数据集只要采用 `actual_grade_v1`，未完成人审会阻止 grading、evidence 和 workflows 的正式采集，不只是阻止流程采集器。

- [ ] 代码及依赖已固定且提交，工作区干净；本机 API 已按最终配置重启，真实模型开发联调通过。
- [ ] 保存新命名批次的原始冻结清单，不覆盖 `final`、`upstream-*`、`execution-*` 历史快照。
- [ ] `dataset.freeze.manifest_sha256` 使用清单文件**原始字节**的 SHA-256；冻结时间带时区，代码 commit、提供方、模型及 endpoint 指纹与清单一致。
- [ ] `chapter_mapping_sha256` 使用 `evaluation.core.digest(bindings["cases"])`；不是整个 bindings 文件的哈希。后者包含 dataset 摘要，会形成循环引用。
- [ ] `response_policy_sha256` 使用 `evaluation.core.digest(完整作答策略JSON)`，包括场景覆盖项和独立问答输入。
- [ ] 把上述人工字段与两个摘要写入最终原始 dataset 后，重新计算 dataset digest，更新运行 bindings 的 `dataset_sha256`；用此原始快照分别运行全部采集器。
- [ ] 保存哈希清单、候选聚合来源、实际夹具表、两人复核记录和最终版本。此后代码、模型、输入、检索/提示、映射或策略变化都建立新命名批次，不改旧观察结果。

## 第二阶段：采集实际输出

此阶段由采集工具执行，不能把开发 smoke、依赖注入运行或 `controller_records` 当成正式结果。

1. 先验证原始 dataset 与运行身份，再分别运行实际 grading、evidence、workflows。grading 必须显式提供 `--manifest` 和 `--run`；不带 `--run` 只复制原输入，不采集也不构成模型证据。
2. 各采集器都读取同一份**尚无预测的原始 dataset**。不能把已写 grading 的新 dataset 继续作为 evidence 的输入，以免原始绑定摘要变化。
3. 保留真实答案、引用、二元评分/命中索引、每次流程的动作/轮次/最终报告及使用量日志。流程共 120 次观察，三角色共享首轮的实际成本不能重复算成三次物理调用。
4. 检查点中的请求 intent 没有结果时，先核对实际已保存记录，再决定恢复；不自动重放未知请求，不删除检查点来掩盖失败。
5. 合并三个采集结果成为新的 `observed-dataset.json`。保存原始输入和各采集输出，不覆盖历史。无 token、无单价、无耗时记录时保留未知值，不写成零。

- [ ] 两人拿到的是完整观察快照与其新摘要；所有未完成、失败或不确定运行仍明确可见。
- [ ] 已确认 baseline/full 的比较范围。证据问答当前固定为同一生产 QA 路径，不将结果描述为检索消融实验。

## 第三阶段：两人分别独立标注

针对**合并后的实际观察快照**重新执行：

```powershell
python -m evaluation labels path/to/observed-dataset.json --output-dir logs/human-review-new
```

成员各持一份新生成的 `annotator-a.json` / `annotator-b.json` 和原始讲义，独立工作后才互相查看。当前每人 140 个标注条目：20 个共享选择题、40 个共享简答、40 个证据问题的两个系统答案。工作流运行的程序迹线另由冻结协议检查。准备阶段的旧空表不能套用到新输出摘要。

工具的盲标工作项隐藏机器二元判分和选择题候选 key；证据输出仍包含 variant 字段，因此不能把它描述为对系统身份完全双盲。如项目要求更强盲法，应在采集前另行固定编码映射和解盲步骤。

| 类型 | 每位成员独立填写的内容 |
| --- | --- |
| 选择题 | 作答是否正确、原始支持页；题意、来源支持、候选答案正确性及重复性审核 |
| 简答 | 命中的零基评分点索引、支持页和题目审核；完整检查所有点，不能只看机器判分 |
| 证据问答 | 问题是否受讲义支持、回答正确性、覆盖的参考点、声明划分是否完整、每条声明是否被其引用的有效教学页完整支持、无关引用 |

- [ ] 两位成员各自核对声明划分；段落只是候选声明边界。漏掉的事实、只支持半句话、空引用、错页、归属页或网页来源均不能当作完整的讲义支持。
- [ ] 对不可由讲义支持的问题，分别判断拒答是否合适；不能仅因为系统标记 `refused` 就判为正确，也不能用网页答案冒充冻结讲义支持。
- [ ] 若必须更改观察快照的声明划分，保留原回答和原版本，先生成新的观察快照与摘要，再重新生成两份表；不把旧表摘要改一行后继续使用。
- [ ] 每人自行填写自己的真实 `annotator_id`、human 来源及完成独立作业的声明；未完成时保留空值，不由助手代签。
- [ ] 两份原始独立表分别保存，完成独立阶段前不抄对方判断，不把 AI 建议或机器候选提示当成人工标签。

## 第四阶段：共同裁决与正式报告

```powershell
python -m evaluation adjudication path/to/observed-dataset.json --annotator path/to/annotator-a.json --annotator path/to/annotator-b.json --output-dir logs/adjudication-new
```

工具只列出分歧并生成空白裁决表，不自动选任何一人的答案。两人共同回看原页与作答，在 `adjudication.json.labels` 填入一致决定和非空理由，记录裁决者及两位原标注者 ID。保留原始两份表；没有分歧时无需伪造裁决条目。

- [ ] 所有分歧都已实际复核，或仍明确标记未解决；不能静默丢弃不一致条目。
- [ ] 用观察快照、两份独立表、必要的裁决表和实际用量日志执行 `score --require-complete`。
- [ ] 仅在输入有效、实际观察及人工判断完整时报告正式通过/未通过。缺失项保持 pending，`official_accepted` 保持未知，不能把“采集完成”当作“达到目标”。
- [ ] 对照预先冻结的目标：选择题一致率 100%，简答一致率至少 80%，引用支持率至少 85%，流程至少 18/20 场景通过，禁止错误为零。
- [ ] 报告保留失败、未覆盖、实际 token/耗时与成本未知项，并说明结果不证明真实学生学习成效提高。

运行字段及完整命令以 [正式采集说明](FORMAL-COLLECTION.md) 和 [评估说明](EVALUATION.md) 为准。
